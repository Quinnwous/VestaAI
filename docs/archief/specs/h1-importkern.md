# H1 — Importkern + importscript (fase 5.2, formaat-onafhankelijk deel)

Je werkt in de VestaAI-repo (Next.js 14 + Supabase), in je eigen git-worktree. Lees eerst CLAUDE.md, `docs/roadmap.md` § 3.1 (datalagen) en § Fase 5 (items 5.2), en de migratie `supabase/migrations/20260917_transacties_pijplijn.sql` (tabel `imports`, kolommen `bron`, `import_id`, `adres_sleutel`, `geocode_status`, `uitgesloten_reden`, `aankopend_kantoor`, `verkopend_kantoor_norm` bestaan al op productie — **geen migratie nodig**).

## Context
De echte Brainbay- en Realworks-exports van i4housing zijn er nog niet. We bouwen nu alles wat níet afhangt van hun exacte kolomnamen, zodat we bij binnenkomst alleen nog de kolomaliassen per bron hoeven te zetten. Bestaande bouwstenen die je hergebruikt (niet dupliceren): `lib/transactieImport.ts` (`parseCsv`, `ALIASSEN`, `TransactieInsert`), `lib/transactieNormalisatie.ts` (`adresSleutel`, `parseAdresVrijeTekst`, `woningtypeGroep/Sub`), `lib/importSnapshot.ts` (contract voor `imports.snapshot_json` — **volg dit exact**, een andere agent bouwt het terugdraaien erop).

## Opdracht (commit na elke stap)
1. **`lib/rd.ts`** — RD (EPSG:28992) → WGS84, pure functie `rdNaarWgs84(x, y) → { lat, lng }` (benaderingsformules van Schreutelkamp/Strang van Hees volstaan, nauwkeurigheid < 1 m). Plus `isRdCoordinaat(x, y)` (bereik NL: x 0–300.000, y 289.000–629.000). Test: Amersfoort (155000, 463000) → 52,155172 N / 5,387203 O (± 0,00001), plus een tweede bekend punt.
2. **`lib/kantoorNormalisatie.ts`** — `normaliseerKantoornaam(naam)`: lowercase, diakrieten weg, zonder B.V./BV/Makelaars/Makelaardij/NVM/o.g./& Partners-achtige ruis en leestekens, witruimte samengevoegd (bv. "i4 Housing B.V." en "I4housing Makelaars" → beide dezelfde norm; beslis of spaties in de norm blijven en test het). `isEigenKantoor(naam, aliassen)` op de norm. Voeg `kantoor_aliassen: z.array(z.string()).optional()` toe aan `KantoorInstellingenSchema` in `lib/schemas.ts` (alleen dat veld). Tests met realistische varianten.
3. **`lib/transactieKwaliteit.ts`** — `beoordeelTransactie(rij) → { uitgesloten_reden: string | null }` met plausibiliteitsregels uit de roadmap: prijs € 50k–10 mln, woonoppervlak 20–1.000 m², € per m² 500–15.000, bouwjaar 1600–(huidig jaar + 1), verkoopdatum niet in de toekomst en niet vóór 2000, verplichte velden (adres_sleutel, verkoopprijs, verkoopdatum). Reden-codes als vaste union (`'prijs_onwaarschijnlijk'` …), plus een NL-label per code. Uitgesloten rijen worden wél opgeslagen (met `uitgesloten_reden`), zodat het rapport ze kan tonen — controleer in `lib/transactiesQuery.ts` / de RPC's of `uitgesloten_reden is null` al wordt gefilterd; zo niet, meld dat in je oplevering (niet zelf RPC's aanpassen).
4. **`lib/ontdubbelen.ts`** — `ontdubbel(rijen)`: dubbelen tussen bronnen op `adres_sleutel` + verkoopdatum ± 90 dagen; Realworks wint, ontbrekende velden worden aangevuld uit Brainbay; binnen één bron identieke sleutel+datum → laatste wint. Geeft `{ rijen, samengevoegd: number, voorbeelden }` terug. Tests.
5. **`lib/importProfielen.ts`** — per bron (`brainbay`, `realworks`) een profiel: extra kolomaliassen bovenop `ALIASSEN`, datumformaat(en), decimaal-/duizendtalnotatie, of coördinaten RD of WGS84 zijn. Vul met je beste gok op basis van publiek bekende exportkoppen, **duidelijk gemarkeerd als voorlopig** (commentaar: wordt definitief in 5.1 exportanalyse). Exporteer ook de mapping-functie `mapRij(ruweRij, profiel) → TransactieInsert-achtig + bron`. Hergebruik de parse-helpers uit `transactieImport.ts` (exporteer ze daar zo nodig; gedrag van de admin-CSV-import mag niet veranderen — de bestaande tests moeten groen blijven).
6. **`lib/importPijplijn.ts`** — pure orkestratie: ruwe rijen → mappen → normaliseren (`adres_sleutel`, woningtype, `verkopend_kantoor_norm`, `eigen_verkoop` via aliassen) → kwaliteit → ontdubbelen → `{ rijen, rapport }`. Rapport: aantallen per uitsluitreden, top-10 voorbeelden per reden, verdeling per plaats en per jaar, % met coördinaat, aantal eigen verkopen. Plus `bouwSnapshot(bestaandeRijen, nieuweRijen)` volgens `lib/importSnapshot.ts` (welke rijen zijn nieuw vs. bijgewerkt, vorige waarden van alleen de geschreven kolommen, `afgekapt` boven `MAX_SNAPSHOT_RIJEN`). Uitgebreide tests, liefst op een kleine synthetische set die beide bronnen en alle randgevallen raakt.
7. **`scripts/import-transacties.mjs`** — `--bron brainbay|realworks --bestand <pad> --kantoor <id> [--write]`. Leest CSV én XLSX (`xlsx`/SheetJS als **devDependency**, alleen in het script). Standaard dry-run: print het rapport, schrijft niets. `--write`: weigert als er geen back-up van vandaag is (kijk hoe `scripts/backup-data.mjs` zijn bestanden wegschrijft en controleer daarop), haalt bestaande rijen op (kantoor_id + adres_sleutel + verkoopdatum), schrijft eerst een `imports`-rij (`status 'bezig'`), upsert in batches van 500 met `import_id` en `onConflict: 'kantoor_id,adres_sleutel,verkoopdatum'`, en zet daarna `status 'klaar'`, aantallen, `kwaliteitsrapport_json`, `snapshot_json`, `klaar_op` (bij fout: `status 'mislukt'`). Service-client met een **harde `kantoor_id`-filter** in elke query (zie het patroon en de toelichting in `scripts/backtest-waardering.mjs`). Kijk hoe bestaande scripts `.ts`-modules uit `lib/` importeren en doe het hetzelfde. **Draai het script NIET met `--write`**; een dry-run op een synthetisch testbestand dat je zelf in `scripts/fixtures/` of een tempmap maakt is prima (die dry-run leest alleen, maar leest wel van productie — mag).

## Regels
- TypeScript strict, geen `any`. Pure functies in `lib/` met vitest-tests (zie bestaande `*.test.ts` voor stijl). Nederlandse namen en commentaar, zoals de rest van de code.
- Commit na elke deelstap, Nederlandse commitberichten, eindigend met `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Niet pushen.
- DoD: `npm run typecheck && npm run test && npm run build` groen. `dod:screens` en `lib/maplibreWorker.guard.test.ts` werken niet in een worktree — de hoofdsessie draait die. Kopieer geen `.env.local`; heb je voor de dry-run env nodig, sla die stap dan over en meld het.
